# Протокол восстановления Keenetic

Разбор `krutil_en.exe` (1 680 832 байта, PE32 MFC, «Keenetic Operating System
Recovery») и формата recovery-образа. Всё, что здесь описано, получено
статическим анализом и проверено арифметикой на реальном файле
`KN-1221_recovery.bin`; ничего не проверялось на живом роутере в режиме
восстановления.

## 1. Как устроена Windows-утилита

Импорты, которые определяют поведение:

| Библиотека | Функции |
|---|---|
| `WSOCK32.dll` | `socket`, `bind`, `connect`, `send`, `recv`, `recvfrom`, `select`, `setsockopt`, `ioctlsocket`, `htons`, `ntohs` |
| `IPHLPAPI.DLL` | `GetAdaptersInfo`, `AddIPAddress`, `DeleteIPAddress` |

Строки, по которым восстанавливается сценарий:

```
ERROR: TFTP port is occupied by another application
ERROR: socket is not created
ERROR: IP address 192.168.1.2 is used by the adapter:
ERROR: unable to open a list of available files: fw.ini
ERROR: System Image File is missing from the list:
ERROR: System Image File is corrupted or not supported:
ERROR: unable to open Keenetic System Image File:
Keenetic operating system successfully recovered!
192.168.1.2
%s\fw.ini
%s\fw\%s
```

Отсюда сценарий целиком:

1. Утилита поднимает **TFTP-сервер на UDP-порту 69** (`htons(69)` перед
   `bind`, сокет создаётся как `socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP)`).
2. Адрес компьютера выставляется в **192.168.1.2** через `AddIPAddress`;
   если адрес уже занят — ошибка «IP address 192.168.1.2 is used by the
   adapter». Роутер в режиме восстановления — **192.168.1.1**.
3. Роутер сам приходит на `192.168.1.2:69` с TFTP-запросом на чтение (RRQ).
   Утилита ничего не опрашивает — она только отвечает.
4. По имени файла из запроса выбирается образ из списка `fw.ini`,
   файл читается из подкаталога `fw\` и отдаётся блоками.

Признаков широковещательного поиска или отдельного протокола обнаружения в
бинарнике нет: единственный сетевой сценарий — TFTP-сервер.

## 2. Формат `fw.ini`

Текстовый файл, по строке на образ. Поля разделяются двоеточием:

```
<имя, которое просит роутер>:<файл в каталоге fw/>:<описание>
```

Файл из комплекта KN-1221:

```
KN-1221_recovery.bin:KN-1221_recovery.bin:Keenetic Launcher (KN-1221)
```

Разбор подтверждается кодом: строка читается, затем делится по символу
`0x3a` (`':'`), после чего первый токен сравнивается с именем файла из
TFTP-запроса. Третий токен — описание для интерфейса, оно же выводится как
«Device model:».

Практический вывод: **модель определяется по имени файла, которое просит
роутер**, а не активным опросом. `kn-recovery` поэтому печатает фактически
запрошенное имя и сверяет его с моделью из трейлера прошивки, но файл отдаёт
в любом случае — образ всё равно один.

## 3. Формат recovery-образа

Образ — это `uImage` плюс 60-байтовый трейлер `ZNBG` в конце файла.

### Заголовок uImage (64 байта, big-endian)

| Смещение | Размер | Поле |
|---|---|---|
| `0x00` | 4 | магия `0x27051956` |
| `0x0C` | 4 | размер данных |
| `0x10` | 4 | адрес загрузки |
| `0x1C` | 1 | OS id |
| `0x1D` | 1 | архитектура |
| `0x20` | 32 | имя образа, например `MIPS OpenWrt Linux-6.18.52` |

### Трейлер `ZNBG` (60 байт, little-endian)

| Смещение | Размер | Поле |
|---|---|---|
| `+0x00` | 4 | магия `ZNBG` |
| `+0x04` | 4 | флаги/тип образа |
| `+0x08` | до 40 | имя модели, `KN-1221`, с нулём на конце |
| `+0x38` | 4 | CRC32 тела образа |

### Контрольная сумма

Проверено на реальном файле:

```
размер файла            = 6 094 908 (0x5D003C)
смещение трейлера       = 0x5D0000
магия                   = 'ZNBG'
модель                  = 'KN-1221'
флаги                   = 0x00801221
CRC32 в трейлере        = 0xA5FF9457
~zlib.crc32(тело)       = 0xA5FF9457   ← совпало
zlib.crc32(тело)        = 0x5A006BA8   ← не то
```

То есть CRC считается по всем байтам до трейлера и берётся в инвертированном
виде:

```python
crc = (~zlib.crc32(data[:len(data) - 0x3C])) & 0xFFFFFFFF
```

Проверка «размер ≥ 1 МиБ» тоже взята из утилиты: она сравнивает длину файла с
`0x100000`, прежде чем искать трейлер.

## 4. Обмен по TFTP

Обычный TFTP (RFC 1350) на порту 69:

```
клиент (роутер)                         сервер (компьютер)
    |  RRQ  "KN-1221_recovery.bin" octet   |
    | -----------------------------------> |
    |                     DATA блок 1 (512) |
    | <----------------------------------- |
    |  ACK блок 1                           |
    | -----------------------------------> |
    |                     DATA блок 2       |
    | <----------------------------------- |
    |  ...                                  |
    |                     DATA блок N (<512)|
    | <----------------------------------- |
    |  ACK блок N                           |
```

Что видно в коде утилиты:

* сокет для передачи данных открывается **отдельно** от слушающего порта 69,
  то есть подтверждения приходят на эфемерный порт — как и требует TFTP;
* блок данных — 512 байт;
* таймаут ожидания — 500 мс, повторов на блок — до 4, после чего утилита
  сдаётся;
* конец передачи — блок короче 512 байт;
* при ошибке клиенту отправляется пакет `ERROR` (opcode 5).

`kn-recovery` реализует то же самое, но с более щедрыми значениями по
умолчанию (таймаут 1 с, 6 повторов) — их можно изменить флагами
`--timeout` и `--retries`.

### Коды ошибок TFTP

| Код | Значение |
|---|---|
| 1 | файл не найден |
| 2 | доступ запрещён |
| 3 | диск переполнен |
| 4 | недопустимая операция |
| 5 | неизвестный идентификатор передачи |
| 6 | файл уже существует |
| 7 | нет такого пользователя |

## 5. Порядок действий из интерфейса утилиты

Строки инструкции в бинарнике:

```
1. Disconnect all network cables from the Keenetic and turn off its power.
2. Connect the computer by Ethernet cable to one of the network ports of the Keenetic.
3. Press the Reset button located on the back of Keenetic and while holding it,
   turn in the power of the Keenetic.
4. Release the button "Reset" when Keenetic indicator "Status" will start flashing.
```

После успешной передачи утилита показывает «Keenetic operating system
successfully recovered!» — запись во flash и перезагрузку роутер делает сам.

## 6. Что осталось непроверенным

* Точное имя файла, которое запрашивает конкретный загрузчик, подтверждается
  только на живом устройстве; `fw.ini` даёт ожидаемое значение
  `KN-1221_recovery.bin`.
* Поведение при запросе с опциями (`blksize`, `tsize`) в бинарнике явно не
  обрабатывается — утилита, похоже, их игнорирует и всегда шлёт по 512 байт.
  `kn-recovery` тоже не согласовывает опции, но печатает их в отчёте.
* Точный смысл поля флагов `+0x04` не установлен (у KN-1221 — `0x00801221`).
